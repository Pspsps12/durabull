Durabull is designed for operators who need clear visibility into BullMQ queues and fast actions during incidents.

If you are brand new, read this page first, then move into the deeper workflow pages.

## The Main Areas of the App

| App Area | What it helps with | Read next |
| --- | --- | --- |
| Queues Dashboard | See queue health and spot bottlenecks quickly | [Queues Dashboard](/documentation/workflows/queues-dashboard) |
| Queue Detail | Pause/resume, purge, clean, and delete safely | [Queue Operations](/documentation/workflows/queue-operations) |
| Jobs | Inspect payloads, logs, stacktraces, and retries | [Job Lifecycle and Debugging](/documentation/workflows/job-lifecycle-and-debugging) |
| Scheduled Jobs | Create, inspect, and remove recurring schedulers | [Scheduled Jobs](/documentation/workflows/scheduled-jobs) |
| Workers | Confirm workers are connected and active | [Workers Topology](/documentation/workflows/workers-topology) |
| Redis Key Explorer | Inspect non-BullMQ keys safely | [Redis Key Explorer](/documentation/workflows/redis-key-explorer) |

## A Simple Daily Workflow

1. Choose the correct connection for the environment you want to inspect.
2. Open **Queues Dashboard** and check waiting/active/failed trends.
3. Drill into the queue that looks unhealthy.
4. Review failed jobs, logs, and stacktraces.
5. Confirm scheduler and worker state if delays continue.
6. Use destructive actions only after queue-name confirmation and safety checks.
